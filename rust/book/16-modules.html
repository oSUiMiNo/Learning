mod は namespace に似ていますが、役目が 2 つあります。 ファイル分割の仕組みでもあり、公開範囲の仕組みでもあります。

そして C# といちばん違うのは、既定が非公開だという点です。 pub を書いたものだけが外に出ます。

用語の整理

Rust意味C# なら
パッケージCargo.toml 1 つぶんプロジェクト（.csproj）
クレートコンパイルの単位。実行ファイルかライブラリアセンブリ（.dll / .exe）
モジュールクレートの中の入れ物namespace
ワークスペース複数パッケージのまとめソリューション（.sln）
名前空間とファイルの関係が違う

C# では namespace とフォルダ構成は無関係です（慣習で揃えるだけ）。 どのファイルにどの namespace を書いても通ります。

Rust ではモジュールの木がファイル構成と一致します。 mod geometry; と書けば geometry.rs か geometry/mod.rs が読まれます。

そのぶん自由度は下がりますが、「この型はどのファイルにあるか」が パスから確実に分かるという利点があります。

ファイル分割

この章のサンプルは 3 ファイルに分かれています。まず入口です。

mod geometry; の 1 行が「geometry.rs を読み込む」宣言です。

さらに入れ子のモジュールは、同名のフォルダに置きます。

mod と use は別のもの
やることC# なら
mod foo;ファイルを木に組み込む（対応するものが無い）
use foo::Bar;名前を短く使えるようにするusing ディレクティブ

mod を書き忘れると、ファイルは存在してもコンパイルされません。 「ファイルを作ったのに use で見つからない」という詰まり方の原因はこれです。

逆に use は書かなくても、フルパスで書けば動きます。 use は純粋に短く書くためのものです。

公開範囲

書き方見える範囲C# なら
（何も書かない）同じモジュールの中だけprivate
pubどこからでもpublic
pub(crate)同じクレートの中だけinternal
pub(super)親モジュールまで—
pub(in path)指定したモジュール以下—
既定が違う

C# のクラスメンバは既定で private、型は既定で internal です。 Rust はすべて既定で「そのモジュールの中だけ」です。

つまり pub struct Point と書いても、 フィールドは pub を付けないと外から見えません。

pub struct Point { x: f64, // 外からは触れない pub y: f64, // 外から触れる }

「型は公開するが中身は隠す」を素直に書けます。 C# でプロパティを書いてフィールドを隠すのと同じ効果が、既定で得られます。

実行結果を見ると、非公開のものも「公開関数を通せば使える」ことが分かります。

パスの書き方

書き方意味
crate::geometry::areaクレートの根から辿る（絶対パス）
self::areaいまのモジュールから
super::Point親モジュールから
geometry::Pointいまのモジュールから見える名前で（相対パス）
use の便利な書き方
use std::collections::{HashMap, HashSet}; // まとめて use std::io::{self, Write}; // io 自身も一緒に use std::collections::HashMap as Map; // 別名を付ける（C# の using X = Y） use std::fmt::*; // 全部（避けたほうがよい） pub use crate::geometry::Point; // 再公開（外から見えるようにする）

最後の pub use が便利です。 内部の構成を隠しつつ、使いやすい名前で公開できます。 ライブラリの lib.rs でよく使われる書き方です。

外部クレートを使う

crates.io からライブラリを持ってきます。第 3 章で見た cargo add です。

cargo add rand

足したら、use で名前を持ってくるだけです。

use rand::RngExt; let n = rand::rng().random_range(1..=100);
2015 エディションの extern crate は不要

古い記事には、ファイルの先頭に次のように書くよう指示されているものがあります。

extern crate rand;

2018 エディション以降は不要です。 Cargo.toml に書いてあれば、そのまま use できます。

いま cargo new で作ると 2024 エディションになるので、 extern crate を見かけたら「その記事は 2018 年より前のもの」と判断できます。

クレートを探すとき

docs.rs は必ず使ってください。 公開されているすべてのクレートの、すべての版のドキュメントが揃っています。 cargo doc --open でローカルにも作れます。

実務では lib.rs に中身を書き、main.rs は薄い入口にします。

fn main() -> anyhow::Result<()> { my_tool::run() }

こうすると、中身がライブラリなので結合テストから呼べるようになります。 main.rs だけに書くとテストしづらくなります。

ワークスペース

複数のパッケージをまとめて扱いたいときは、 ルートに Cargo.toml を置いてワークスペースにします。

[workspace] resolver = "3" members = ["core", "cli", "server"]

target/ が 1 つに集約されるのでビルドが速くなり、 ディスクの節約にもなります。 この教材の examples/ も 20 個のプロジェクトをワークスペースにまとめています。

resolver = "3" は依存解決の新しい方式です。 2024 エディションではこれを指定します。

やってみよう
  1. examples/16-modules を動かしてください。
  2. geometry.rs の pub struct Point の x に pub を付けて、main.rs から a.x と書けるようになることを確認してください。
  3. main.rs から mod geometry; を消して、どうなるか見てください。
  4. doubled_distance から pub を消して、E0603 を出してください。
  5. 新しいモジュール src/util.rs を作って、main.rs から呼べるようにしてください。

この章のまとめ

  • mod はファイルを木に組み込む。use は名前を短くする。別のもの。
  • モジュールの木はファイル構成と一致する。C# の namespace とは違う。
  • 既定は非公開。pub / pub(crate)（＝internal）を付けて出す。
  • pub struct のフィールドは、個別に pub が必要。
  • extern crate は 2018 エディション以降不要。あったら古い記事。
  • 中身は lib.rs、main.rs は薄い入口にするとテストしやすい。
  • クレートを調べるときは docs.rs。
