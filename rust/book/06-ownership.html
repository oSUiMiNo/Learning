先に答えを書きます。Rust の規則はこの 3 行だけです。

所有権の 3 つの規則
  1. すべての値には持ち主（owner）がひとりだけいる。
  2. 持ち主は同時にひとりだけ。別の変数に渡すと、持ち主が移る。
  3. 持ち主がスコープを抜けると、値はその場で片付けられる。

これだけで、GC なしでメモリが正しく片付き、 かつ「解放したものを見てしまう」事故が起きなくなります。 順番に見ていきましょう。

まずスタックとヒープ

所有権の話は、値がどこに置かれているかを知らないと分かりません。 C# でも「値型はスタック、参照型はヒープ」と習ったと思いますが、その区別がそのまま効きます。

図の右下が問題です。ヒープに置いたものは、誰かが片付けなければなりません。

言語誰が片付けるか代償
C#ガベージコレクタ実行時のコストと、いつ動くか分からない停止
C / C++書いた人が free / delete を呼ぶ忘れると漏れる。2 回呼ぶと壊れる
Rust持ち主がいなくなった時点で自動的に持ち主の規則をコンパイラに納得させる手間

Copy される型と move される型

代入したときのふるまいが、型によって 2 通りあります。

let a = 10; let b = a; println!("{a} {b}"); // どちらも使える
let s1 = String::from("こんにちは"); let s2 = s1; println!("{s1}"); // ✗ s1 はもう使えない

実際にコンパイルすると、こう言われます。

エラーの読み方を覚えておくと、これから何度も助かります。

出ている行言っていること
move occurs because ... does not implement the `Copy` trait この型は複製されない、と教えている
value moved here所有権が移った場所
value borrowed here after move移った後に触ってしまった場所
help: consider cloning the value ...直し方の提案

そして move の瞬間に何が起きているかが、これです。

なぜ「両方使える」ではいけないのか

もし s1 も s2 も使えるとすると、 スコープを抜けるときに同じヒープ領域を 2 回解放してしまいます。 これは C++ で「二重解放」と呼ばれる、深刻な不具合の原因です。

かといって「参照カウントを持って、最後の 1 人が解放する」方式にすると、 C# のような実行時コストが発生します。 Rust は「持ち主はひとりだけ」と決めることで、どちらも避けました。 片付けるのは常に持ち主ひとりなので、カウントも GC も要りません。

C# の値型・参照型との対応
C#Rust
小さい値値型（int, struct）→ コピーCopy な型 → コピー
大きい値参照型（class）→ 参照がコピーされ、両方から同じ実体を見る→ 所有権が移り、元は使えなくなる

C# で var b = a;（a がクラス）と書いたとき、 a も b も同じオブジェクトを見ます。これが Rust では通りません。 「参照型を代入したら両方から見える」という C# の直感が、 最初につまずく原因です。

見分け方は「ヒープを持っているか」です。 ヒープを持つ型は、丸ごとコピーすると高いので move になります。

自分の型を Copy にする

フィールドが全部 Copy なら、derive で Copy にできます。

#[derive(Debug, Clone, Copy)] struct Point { x: i32, y: i32 }

Copy には Clone も必要です。 String を含む型は Copy にできません。

関数に渡すと所有権も渡る

代入と同じことが、引数でも起きます。ここが実務でいちばん引っかかる場所です。

「関数を呼んだら変数が使えなくなった」

C# で Consume(message) と書いても、 message はその後も使えます。参照が渡るだけだからです。

Rust で consume(message) と書くと、 message の所有権が関数に移ります。 関数が終わるとそこで片付けられるので、呼び出し側には返ってきません。

直し方は 3 つあります。ほとんどの場合、正解は 1 番目です。

やり方書き方使う場面
1. 借りるfn peek(text: &str)読むだけならこれ。第 7 章の主題
2. 複製するconsume(message.clone())本当に 2 つ必要なとき
3. 返してもらうlet m = shout(m);加工して返す形にしたいとき

初心者のうちは clone() を貼って前に進んでも構いません。 動かないコードより、少し遅いコードのほうがましです。 慣れてきたら借用に置き換えていけばよいのです。

スコープを抜けると片付けられる

3 番目の規則です。持ち主がいなくなった瞬間に drop が呼ばれます。

IDisposable と Drop
C#Rust
後片付けを書く場所Dispose()impl Drop for T { fn drop(&mut self) }
呼ぶきっかけusing を書く / 手で呼ぶ自動。所有者が消えた時点
書き忘れると解放されない起こりえない
自分で呼べるか呼べる（複数回呼ぶ危険もある）呼べない（drop(値) に渡す）

Drop は「所有権が消える場所」に紐づいているので、 C# の using より漏れません。 ファイル・ソケット・ロックの解放が、全部この仕組みに乗っています。 第 19 章の Mutex でロックの外し忘れが起きないのも、これのおかげです。

この章のまとめ

  • 値には持ち主がひとりだけ。持ち主が消えたら値も片付けられる。
  • 小さい型（i32 など）は代入でコピー。ヒープを持つ型（String, Vec）は move。
  • 関数に渡すのも move。読むだけなら借りる（第 7 章）のが正解。
  • 困ったら clone() で前に進んでよい。後で借用に置き換えられる。
  • Drop は IDisposable に当たるが、書き忘れようがない。
  • E0382 が出たら、value moved here の行を見て「どこで手放したか」を探す。
