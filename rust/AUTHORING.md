# Rust 入門を作って分かったこと

この教材（全 23 章）を 1 冊まるごと作る過程で、
**実際に詰まったこと・実際に間違えたこと**を書き残したものです。
ここに書いてあるのは全部、本当に起きたことです。

分野を問わず効くこと（正しさの担保、書き方、進め方、チェックリスト）は
リポジトリ直下の **[AUTHORING.md](../AUTHORING.md) — 教材づくりの共通ルール** にあります。
**先にそちらを読んでください。** この文書はその続きで、
Rust / コンパイラ / CLI 特有の話だけを扱います。

> この教材で得たナレッジのうち、分野を問わず効くと判断したものは
> 共通編に昇格させてあります（2-1 の版の取り違え、2-3 の兄弟スクリプトの取り残し、
> 3-5 の実測と再現の線引き、5-1 の既知言語からの橋渡し）。
> 新しい教材を作ったときも、同じように**両方を更新**してください
> （切り分けの基準は共通編の 8 節）。

## 1. この教材で「実物」をどう捕まえたか

共通ルールの 1 節が言う「この分野で実物とは何か」への、この教材なりの答えです。

GUI 教材と違い、Rust には**見せる画面がありません**。
かわりに実物が 3 つあり、それぞれ別の方法で捕まえています。

```
examples/NN-name/     ←── 本文がビルド時に読み込む（書き写さない）
      │
      ├──→ cargo build / test / run / fmt / clippy   … 動くことの担保
      └──→ 擬似端末で実行 → ANSI ごと捕獲 → 本文に載る

examples/errors/*.rs  ←── 「わざと通らない」コード
      │
      └──→ rustc --error-format=json → 宣言したエラーコードと照合
```

**3 つめが、この教材でいちばん効いた仕組みです。**

Rust の入門書では「これはコンパイルエラーになります」という例が主役になります。
ところがこの手の記述は、言語の変化でいちばん先に嘘になります。
借用検査が賢くなって通るようになったり、エラーコードが変わったりするからです。

そこで各サンプルの先頭に期待するエラーコードを書き、実物と突き合わせています。

```rust
//! expect: E0382
//! title: move した後の変数を使ってしまう
//! chapter: 06-ownership
```

`expect: ok` と書けば「通ること」も確かめられます。
第 7 章の非語彙的ライフタイム（NLL）の説明は、これを使って
**「昔はエラーだったが、いまは通る」ことを実測で示しています**。
古い記事の「Rust の借用検査は厳しすぎる」という記述が、
いま当てはまらないことの根拠になっています。

| ツール | 何を担保しているか |
|---|---|
| `tools/check_examples.py` | 全サンプルが build / test / run / fmt / clippy(`-D warnings`) を通る |
| `tools/check_errors.py` | 「通らない例」が、宣言どおりのエラーコードで落ちる |
| `tools/check_crates.py` | 外部クレートの API についての記述が、実物と合っている |
| `tools/capture.py` | 端末出力が、実際にコマンドを走らせて得たものである |
| `tools/build.py` | 未解決の指示子・壊れたリンク・欠落した図や出力がない |
| `tools/preview.py` | 表示崩れがなく、掲載コードが実ファイルと 1 バイトも違わない。**実測/再現バッジが全ターミナル枠に付いている** |

## 2. やらかした間違い

### 2-1. 「最新版」を取り違えた。原因はインデックスの並び順

**この教材でいちばん大きい間違いです。**

付録に「古い記事との差分」表を書くため、`rand` クレートの最新版を調べました。
crates.io の sparse index を取得し、**最終行を最新版として採りました**。
出た答えは `0.9.5`。それを前提に付録を書きました。

実際に `cargo add rand` を走らせたら、入ったのは **`0.10.2`** でした。

原因は単純です。**インデックスは公開時刻順であって、版の大小順ではありません。**
`rand` の末尾はこうなっていました。

```
0.10.1
0.9.4
0.8.6
0.10.2     ← semver では最大
0.8.7
0.9.5      ← 最終行。これを採ってしまった
```

`0.10.2` が出たあとに、旧系列の保守リリース `0.8.7` と `0.9.5` が続けて公開されています。
複数の系列を並行で保守しているクレートでは、**これがむしろ普通**です。

決めたこと:

- **版の一覧を取ったら、必ず semver として比較して最大を採る。** 最終行を信じない
- そもそも一覧を自分で解釈せず、**そのツール自身に解決させる**のが確実
  （`cargo add` を一時プロジェクトで実行し、書き込まれた `Cargo.toml` を読む）

### 2-2. 版を直しても、まだ間違っていた

`0.10.2` だと分かったので書き方を直そうとしましたが、
ここでもう 1 段間違えました。0.9 の書き方に直しただけだったのです。

実際に 3 通りをコンパイルして確かめました。

| 版 | 書き方 | いま実行すると |
|---|---|---|
| 0.8（記事に最も多い） | `use rand::Rng;` + `thread_rng().gen_range(..)` | **E0425**（`thread_rng` が無い） |
| 0.9 | `use rand::Rng;` + `rng().random_range(..)` | **E0599**（メソッドが生えない） |
| **いま** | `use rand::RngExt;` + `rng().random_range(..)` | 通る |

2 番目がとくに厄介です。`use rand::Rng;` は**成功します**。
`Rng` というトレイトは今も存在するからです。
ところが便利なメソッド群は `RngExt` に移っており、
**import は通るのにメソッドが無い**という、いちばん意味の分からない失敗になります。

対処として `tools/check_crates.py` を書き、
付録の表の各行を**実際にクレートを取得してコンパイル**するようにしました。

```python
dict(
    name="rand-0.9-style-Rng-trait",
    crate="rand",
    source="use rand::Rng;\n"
           'fn main() { let mut r = rand::rng(); let n: u32 = r.random_range(1..=100); println!("{n}"); }',
    expect="E0599",
    note="0.9 までの書き方。Rng は今も存在するので import は通るが、"
         "メソッドが RngExt に移ったので生えない",
)
```

食い違ったら公開が止まります。
**外部クレートの話を書くなら、その版を取ってきて実際にコンパイルしてください。**
記憶でも検索結果でも、この 2 段構えの罠は踏み抜きます。

### 2-3. 出力先を変えたとき、兄弟スクリプトを取り残した

2 冊目を足すにあたり `docs/` の構成を変え、
Qt6 の教材の出力先を `docs/` から `docs/qt6-widgets/` に移しました。
このとき **`tools/build.py` だけを直し、同じ場所を参照している他を見落としました。**

| 取り残したもの | 症状 |
|---|---|
| `shots.py` / `shots_cpp.py` | 画像と `shots.json` を旧パスに書く。**撮り直した瞬間に画面写真が壊れる** |
| `preview.py` | 巡回対象が**ハブ 1 件 ＋ 旧 URL 転送 15 件 ＋ 教材 2 件の計 18 件**になり、対象の 16 ページを 1 つも見ていなかった |

怖いのは 2 つめです。**検証スクリプトが壊れても「問題はありませんでした」と言います。**
落ちてくれないので気づけません。

決めたこと:

- 出力先を変えたら、`grep -rn 'docs' <教材>/tools/` で**同じ場所を参照している全部を洗う**
- 検証スクリプトは、**何件を検査したかを必ず出力する**。
  `preview.py` は「16 ページを検査し」と出すので、数が変われば人間が気づけます

### 2-4. clippy を厳しくしたら 3 件落ちた。直したら教材が良くなった

`cargo clippy -- -D warnings` を既定にしたところ、教材のサンプルが 3 件落ちました。
そのうち 1 件は、こう指摘されました。

```
error: writing `&mut Vec` instead of `&mut [_]` involves a new object where a slice will do
```

第 7 章で「中身を書き換えるので `&mut` が必要」と説明するために
`fn double_all(numbers: &mut Vec<i32>)` と書いていた箇所です。
要素を差し替えるだけなら `&mut [i32]` で足ります。

指摘に従って直したついでに、**個数を変える関数を 1 つ足しました**。

```rust
fn double_all(numbers: &mut [i32]) { ... }        // 要素の差し替えだけ → スライスで足りる
fn append_total(numbers: &mut Vec<i32>) { ... }   // push する → Vec でないと駄目
```

結果として「`&mut [T]` と `&mut Vec<T>` の使い分け」という、
元の原稿には無かった説明が増えました。
共通ルール 2-5 の「間違いを直すと、しばしば元より良くなる」の実例です。

## 3. 端末出力を捕まえるところで詰まった点

GUI 教材のスクリーンショットに当たるものが、この教材では端末出力です。
そこ特有の詰まりどころを並べます。

### 3-1. パイプに繋ぐと色が消える。だから擬似端末で走らせる

`subprocess.run(..., capture_output=True)` で取ると、
cargo も rustc も**色を付けてくれません**。相手が端末でないと判断するからです。

`--color=always` を付ける手もありますが、
**擬似端末 (pty) の上で走らせるほうが実機に近い**と判断しました。
読者の画面で起きることと同じ経路を通るからです。

```python
primary, secondary = pty.openpty()
fcntl.ioctl(secondary, termios.TIOCSWINSZ, struct.pack("HHHH", 40, 92, 0, 0))
proc = subprocess.Popen(command, stdout=secondary, stderr=secondary, ...)
```

端末幅は固定します（ここでは 92 桁）。
**幅が変わると rustc の折り返し位置が変わり、出力が毎回変わってしまう**ためです。
共通ルール 3-2 の「決定性を壊すもの」の、この分野での具体形です。

### 3-2. 擬似端末にするとページャが起動して、撮影が固まる

3-1 の代償です。`rustc --explain E0382` を撮ろうとしたら、**永久に返ってきませんでした。**

相手が端末だと判断した `rustc` が `less` を起こし、
入力待ちのまま止まっていたのです。プロセスを見て初めて分かりました。

```
21770  rustc --explain E0382
21776  less -R          ← これが入力を待っている
```

```python
env["PAGER"] = "cat"
env["RUST_PAGER"] = "cat"      # rustc --explain はこれを見る
env["GIT_PAGER"] = "cat"
```

あわせて、**すべての捕獲に時間制限を入れました**。
1 つ止まっただけで全体が固まる作りにしておくべきではありません。

```python
if proc.poll() is None and time.monotonic() > deadline:
    proc.kill()
    chunks.append(f"\n[capture.py] {timeout:.0f} 秒を超えたため打ち切りました\n".encode())
```

### 3-3. ANSI を HTML にするとき、色指定まで消してしまった

捕獲した ANSI を色付き HTML に変換する処理で、**色が全部落ちました。**

原因は、色以外の制御シーケンス（カーソル移動・行消去）を捨てる正規表現が、
**色指定まで巻き込んで消していた**ことです。

```python
# ✗ 終端が [a-zA-Z] なので \x1b[1m の 'm' にも一致してしまう
OTHER_CSI_RE = re.compile(r"\x1b\[[0-9;?]*[a-zA-Z]")

# ○ 終端から m だけを外す
OTHER_CSI_RE = re.compile(r"\x1b\[[0-9;?]*[a-ln-zA-Z]")
```

この 1 文字を外し忘れると、**エラーにはならず、ただ白黒になります**。
共通ルール 5-1 の「黙って動くほうが危険」がそのまま出た形です。

### 3-4. cargo の進捗表示は、そのままだと二重に写る

`cargo run` の出力には、進捗バーが `\r` で同じ行を上書きした跡が残ります。
素直に HTML にすると、消えたはずの進捗バーと `Finished` が同じ行に並びます。

```
Building [=====>    ] 0/1: hello(bin)      \r\x1b[K    Finished `dev` profile ...
```

行ごとに「最後の `\r` より後ろだけを残す」と、実機で見えるとおりになります。

```python
lines.append(raw.split("\r")[-1] if "\r" in raw else raw)
```

### 3-5. 実測できても、実測として出してはいけないものがある

**これがこの教材でいちばん判断に迷った点です。**

捕獲は Linux 上で行っていますが、読者は Windows で読みます。
`rustup show` は実際に走らせられますが、出てくるのはこれです。

```
Default host: x86_64-unknown-linux-gnu
rustup home:  /root/.rustup
```

Windows の読者にとっては**ただの嘘**です。
実測できるからといって、実測として載せてよいわけではありませんでした。

そこで画面を 2 種類に分け、**見た目で区別できるバッジを必ず付けました**。

| 印 | 何か |
|---|---|
| **実測** | 実際にコマンドを走らせて捕獲した出力 |
| **再現** | この環境では出せない画面。**出典をキャプションに必ず出す** |

`rustup show` は再現に落とし、host triple を `x86_64-pc-windows-msvc` に読み替えました。
`rustup-init.exe` のインストーラ画面も再現です。

**再現の文言は、想像で書きませんでした。** rustup 自身のソースにある表示文字列を使っています。

```rust
// rustup/src/cli/self_update/windows.rs
static MSVC_AUTO_INSTALL_MESSAGE: &str = r#"# Rust Visual C++ prerequisites
Rust requires a linker and Windows API libraries but they don't seem to be available.
```

そしてバッジの付け忘れが起きないよう、**指示子を分けました**。

```
<!--term:  err-e0382 | ... -->   実測バッジが自動で付く
<!--termx: rustup-init | ... --> 再現バッジと出典が自動で付く
```

さらに `tools/preview.py` が、バッジの無いターミナル枠を検出したら公開を止めます。
**人間が付け忘れられない構造にする**のが要点でした。

### 3-6. 実測の出力にも、どこまで手を入れてよいか線を引く

3-5 の続きです。パスだけは Windows 形式に直しています。

| 直すもの | 例 |
|---|---|
| 一時作業ディレクトリ | `/tmp/xxxx` → `C:\rust` |
| 実行ファイルのパス | `target/debug/hello` → `target\debug\hello.exe` |
| クレートの展開先 | `~/.cargo/registry/...` → `C:\Users\you\.cargo\registry\...` |

**エラーメッセージ本文・版番号・コンパイル時間・警告の内容には一切触りません。**
ここを曖昧にすると「実測」の意味が無くなります。
どこまで加工したかは `rust/README.md` と第 0 章の両方に明記しました。

## 4. Rust / cargo の環境まわり

| 症状 | 原因と対処 |
|---|---|
| `cargo new 06-ownership` が弾かれる | パッケージ名は数字で始められない。`--name ch06_ownership` を付け、ディレクトリ名だけ番号にする |
| ワークスペースのコマンドが全部落ちる | メンバーが 1 つでもソース欠けだと `cargo metadata` ごと失敗する。**先に全メンバーのソースを置いてから**でないと何も動かない |
| `cargo fmt` を後から掛けたら本文と食い違った | 掲載コードは実ファイルを読むので、整形すると本文も変わる。**サンプルを書いた直後に必ず `cargo fmt`**。その状態を原本にする |
| 依存を足したいのに `cargo add` が失敗する | ソースが無いとマニフェストを解決できない。`src/main.rs` を置いてから `cargo add` する |
| 教材のサンプルなのに clippy が怒る | 意図して破るなら `#[allow(...)]` と**理由をコメントに**書く。黙って無効化しない |
| `cargo run` に引数を渡したい | `cargo run -- 引数`。`--` を忘れると cargo への引数として解釈される |
| ビルド結果が肥大する | ワークスペースにまとめて `target/` を 1 か所に集約した。`.gitignore` に `rust/examples/target/` が要る |

### 4-1. 版とエディションは、手で書かずに実測する

ページ上部のバッジは、ビルド時に実測した値を出しています。

```python
rustc_v = run("rustc", "--version")
edition = detect_default_edition()     # 一時ディレクトリで cargo new して Cargo.toml を読む
```

エディションを**実際に `cargo new` させて確かめている**のがポイントです。
「いまの既定は 2024 です」という本文の主張が、そのまま検証になります。

### 4-2. Playground との版ずれは、いつか必ず来る

調査したところ、Rust Playground には
`rand 0.10.2` / `tokio 1.53.1` / `serde 1.0.229` と、
**この教材が教えている版とほぼ同じものが載っていました**（偶然ではなく、
どちらも「その時点の最新」を採っているためです）。

将来「その場で実行」を入れるなら、この一致は前提にできません。
Playground の収録クレートは Rust のリリースに合わせて更新されるので、
**教材側とずれる時期が必ずあります**。入れるなら、そのずれを検出する検証が要ります。

## 5. Rust 教材ならではの、説明の工夫

共通ルール 5 節に書いたこと以外で、この教材で効いたものです。

### 5-1. 読者が既に知っている言語との「裏切られる箇所」に囲みを作る

この教材の読者は C# が書けます。
そこで囲みを 1 種類足しました（`.note.csharp`、印は `C#` の文字）。

効いたのは**対応表そのものではありません**。
対応表は調べれば分かります。効いたのは、
**似ているのに違うものを名指しする**ことでした。

| 見た目は同じ | 実は違う |
|---|---|
| `async` / `await` | C# の `Task` は呼んだ時点で走る。Rust の `Future` は **await されるまで 1 行も走らない** |
| 文字列の「長さ」 | C# は UTF-16 の単位数。Rust の `len()` はバイト数。**絵文字で 2 対 4 対 1 に割れる** |
| インターフェースとトレイト | トレイトは**他人の型にも後から実装できる**。拡張メソッドでは代替できない |
| 参照型の代入 | C# は両方から同じ実体が見える。Rust は **move して元が使えなくなる** |

とくに `async` は危険です。C# の癖のまま
「呼んでおいて後で await」と書くと、**並行になっているつもりで直列になります**。
エラーは出ません。

**読者が既に知っている言語があるなら、対応表より
「その知識が邪魔をする箇所」を先に書いてください。**

### 5-2. 「通らないコード」を主役にする

Rust の入門では、動くコードより**動かないコード**のほうが教材価値があります。
所有権も借用もライフタイムも、破ったときに何が起きるかで理解するからです。

そこで `examples/errors/` を独立させ、**15 本すべてに実測のエラー出力を付けました**。
読者が見るのは、私が書いた説明ではなく rustc 自身の言葉です。

エラー出力には `help:` の行があり、**直し方まで書いてあります**。
本文ではその読み方を教えるだけで済みました。

### 5-3. 「昔はエラー、いまは通る」を実測で示す

第 7 章の非語彙的ライフタイム（NLL）は、
`expect: ok` を付けたサンプルで「いまは通る」ことを担保しています。

```rust
//! expect: ok
//! 2018 年より前の Rust ではこれはエラーだった。
//! いまは借用が「最後に使った行」で終わるので通る。
```

古い記事の「Rust の借用検査は厳しすぎる」という記述に対して、
**反証を実測で持っている**形になりました。
これは「古い情報でつまずかせない」という教材の目的に直接効いています。

### 5-4. 症状から引ける表は、コンパイラ言語だと特に効く

共通ルール 5-2 の具体形です。
学習者は `E0502` という番号を持って来ます。原因は知りません。

付録にエラーコードの早見表を置き、**症状 → まず疑うこと → 該当章**の 3 列にしました。
「借用検査に詰まったらこの順に試す」という手順も併記しています。

```
1. 借用の範囲を狭める  2. 値を取り出す（*）  3. clone する  4. 設計を変える
```

**1 から順に試して、通ったところで止めてよい**と明記したのが効いたと思っています。
初心者が最初から最適な形を狙って動けなくなるのを防ぐためです。

### 5-5. 分量は C# 話者向けに削れる

全 23 章のうち、変数と制御フローの 2 章は**差分だけ**にしました。
`let` が既定で不変であること、式指向であること、
C 風の `for` が無いこと。これだけです。

逆に所有権・借用・トレイト・async の 4 章は厚くしました。
**読者が既に持っている知識の分だけ、別の場所に予算を回せます。**

## 6. この教材の構成とツール

ファイル構成と各コマンドの使い方は [README.md](README.md) にあります。
公開前に走らせる順番はリポジトリ直下の `README.md` に一覧があります。

- この教材は `tools/build.py` で `../docs/rust/` を生成します
- 章立ての情報源は `book/toc.py` だけです。ナビも目次も前後リンクもそこから生成されます
- 本文で使える指示子は 4 つ。
  `<!--code:-->`（実ファイル）/ `<!--figure:-->`（SVG）/
  `<!--term:-->`（実測）/ `<!--termx:-->`（再現）
- 再現画面の定義は `book/repro.py` にあります。**出典を書く欄が必須**です
- 捕獲した端末出力は `outputs/*.json` にあります。
  コードを変えたら `tools/capture.py` で撮り直してください
- `tools/check_crates.py` は**ネットワークが要ります**。
  外部クレートを実際に取得してコンパイルするためです
