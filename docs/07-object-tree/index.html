第7章 親子関係とメモリ — 消えるウィンドウの謎

「ウィンドウを出したのに一瞬で消える」「なぜか落ちる」。Python と Qt でオブジェクトの寿命の考え方が違うことが原因です。

PySide6 を触り始めた人が、ほぼ必ず一度は遭遇する現象があります。

ボタンを押したら別ウィンドウが開くようにした。
なのに、開いた瞬間に消える。エラーは何も出ない。

これはバグではなく、Qt（C++）と Python でオブジェクトの寿命の考え方が違うことから起きます。 この章でその正体を押さえておくと、あとで無駄に悩まずに済みます。

Qt 側のルール: 親が子の面倒を見る

Qt では、ウィジェットは親子関係の木を作ります。 そして親が破棄されると、その子孫もまとめて破棄されます。 C++ では自分でメモリを解放しなければならないので、 「親に任せておけば全部片付く」というこの仕組みはとても便利です。

親が設定されるのは、次の 2 つのときです。

親がいる ＝ 同じウィンドウの中に描かれる

第 2 章で「親を持たないウィジェットはそれ自体がウィンドウになる」と書きました。 裏返すと、親を持たせれば、その親の内側に描かれるということです。 QLabel が単体だとウィンドウになり、 レイアウトに入れると部品になるのは、この違いによるものです。

Python 側のルール: 誰も参照しなくなったら消える

一方 Python は、変数が誰からも参照されなくなったオブジェクトを自動的に回収します。 PySide6 では、Python 側のオブジェクトが回収されると、 その裏にある C++ 側のウィジェットも一緒に破棄されます。

直し方は 2 つあります。どちらでもかまいません。

この症状に当てはまったら、まず参照を疑う
  • ウィンドウやダイアログが一瞬で消える
  • QTimer が一度も発火しない
  • アニメーションが始まらない
  • QTranslator を入れたのに翻訳されない

どれも「Python 側で変数を残していないので回収された」が原因の定番です。 self. を付けるか、親を渡すかで直ります。

逆の事故: すでに破棄されたものを触る

参照を残すのとは反対に、C++ 側だけが先に破棄されていることもあります。 このとき Python 側の変数はまだ生きているので、触ると例外になります。

親が破棄されたのに、子を指す Python の変数を持ち続けていた、という状況です。 自分で deleteLater() を呼んだ後に触ってしまった場合にも起きます。

ウィジェットを自分で消したいとき

del widget ではなく widget.deleteLater() を使います。 これは「イベントループが一段落したら破棄してください」という予約で、 シグナル処理の途中で自分自身を消してしまう事故を防げます。

まとめると

状況C++ 側Python 側結果
親あり・変数なし親が保持参照なし○ 生き続ける
親なし・変数あり（self.x）保持者なし参照あり○ 生き続ける
親なし・変数なし（ローカル変数）保持者なし参照なし✗ 消える
親が破棄済み・変数あり破棄済み参照あり✗ 触ると RuntimeError

覚えることはひとつだけです。 「親に持たせるか、self に持たせるか、どちらかは必ずやる」。

やってみよう

ch07_vanishing_window.py を実行し、 ［✗ 消えてしまう開き方］と［○ ちゃんと残る開き方］を押し比べてください。 エラーが 1 行も出ないことを、自分の目で確かめておくのが大事です。 これが「原因が分からない」の正体です。

この章のまとめ

  • Qt では親が子を保持し、親の破棄とともに子も破棄される。
  • PySide6 では、Python 側の参照が消えると C++ 側のウィジェットも消える。
  • ウィンドウが一瞬で消えるのは、ほぼ「ローカル変数のまま放置した」が原因。
  • 対処は self. を付けるか、親を渡すか。
  • 手動で消すときは del ではなく deleteLater()。
