第11章 エラー処理 — 例外のない世界

失敗は投げるのではなく、戻り値で返します。`Result<T, E>` と `?` の 2 つで、try-catch と同じくらい短く書けます。

Rust に例外はありません。失敗は戻り値で返します。

最初は面倒に思えますが、道具は 2 つだけです。 Result<T, E> という型と、? という演算子。 これで try-catch と同じくらい短く書けます。

例外との違い

Option と同じく、ただの列挙型です。 None のかわりに「なぜ失敗したか」を Err に入れられる、という違いだけです。

例外と Result の比較
C# の例外Rust の Result
署名に出るか出ない出る
無視できるかできる（catch {} で握り潰せる）#[must_use] なので警告が出る
伝播のしかた自動（何も書かなくても上へ飛ぶ）? を書く
コスト投げると重い（スタックの巻き戻し）ただの値。ゼロコスト
捕まえ忘れ実行時に落ちるコンパイル時に気づく

一番の実利は 1 行目です。関数の署名を見れば失敗しうるか分かります。 C# では、ドキュメントを読むか実装を追うしかありません。

逆に一番の手間は 3 行目です。伝播を自分で書く必要があります。 それが ? です。

? 演算子

? は「成功なら中身を取り出す、失敗ならその場で return」の省略記法です。

だから ? を並べるだけで、失敗はそのまま上へ伝わります。

? は Result を返す関数の中でしか使えない

? は失敗時に return Err(..) するので、 その関数自身が Result を返していなければなりません。

main で使いたいときは、main の戻り値を変えます。 これは Rust 1.26 から可能になった書き方です。

Option を返す関数の中でも ? が使えます （None なら return None）。 ただし Result と Option は混ぜられません。

自分のエラー型を作る

エラーの種類を列挙型で表すのが定石です。

これに 2 つのトレイトを実装すると、「まともなエラー型」になります。

トレイト役目C# なら
Debug開発者向けの表示（{:?}）—
Display人間向けの文言（{}）Exception.Message
std::error::Error標準のエラーとして扱えるようにする。source() で原因を辿れるException.InnerException
例外クラスとの対応
C#Rust

継承階層で分類列挙型の選択肢で分類
catch (SpecificException e)match err { MyError::Specific(..) => .. }

継承ではなく列挙型なので、ここでも網羅性が効きます。 エラーの種類を足したら、対応し忘れた match が全部エラーになります。

実際に動かす

手で書くのは大変なので、クレートを使う

上のコードは Display と Error を手で実装しています。 説明のためにそうしましたが、実務ではクレートに任せます。

クレート用途使う場面
thiserrorエラー型の定義を楽にするライブラリを書くとき
anyhow種類を気にせず「何かエラー」として扱うアプリを書くとき
使い分けの目安
  • アプリ（実行ファイル）を書くなら anyhow ─ 呼び出し側は「失敗した」ことと理由の文言が分かれば十分なことが多い。
  • ライブラリを書くなら thiserror ─ 使う側がエラーの種類で分岐できるように、型を公開すべき。

anyhow の with_context は特に便利です。 「どのファイルを読もうとして失敗したか」といった文脈を、 エラーを上に投げながら積み上げられます。

panic! はいつ使うのか

Result を返すpanic! する
意味「起こりうる失敗」「起こってはならないこと」
例ファイルが無い、入力が数値でない、通信が切れた配列の範囲外、ゼロ除算、内部の不整合
C# なら想定される例外InvalidOperationException / Debug.Assert
呼び出し側対処できる対処できない。プログラムを直すべき
panic はライブラリでは避ける

panic! は既定でスレッドを終了させます。 ライブラリの中で panic すると、使う側に対処の余地がありません。

「入力が不正なら panic」ではなく「不正なら Err を返す」にしてください。 unwrap() をライブラリのコードに残さない、というのは同じことを言っています。

覚えておくと便利なメソッド

書き方意味
result?失敗なら return。基本はこれ
result.unwrap_or(既定値)失敗なら既定値
result.unwrap_or_else(|e| ..)失敗なら計算して既定値

result.is_ok() / is_err()成否だけ調べる
map_err と ? の関係

? は自動で From による型変換を試みます。 つまり impl From<ParseIntError> for MyError を書いておけば、 s.parse()? がそのまま MyError に変換されます。

thiserror の #[from] はこれを自動生成するものです。 変換を都度書きたい場合は map_err を使います。

やってみよう
  1. examples/11-errors を動かして、4 つの入力の結果を確認してください。
  2. load() の ? を 1 つ消して、どんなエラーになるか見てください。
  3. fn main() を fn main() -> Result<(), ConfigError> に変え、load(cases[1])? と書いてみてください。プログラムが 0 以外で終了し、エラーが表示されます。
  4. "42".parse::<i32>() の結果を let _ = ...; と書かずに放置して、警告が出ることを確認してください。

この章のまとめ

  • 例外は無い。失敗は Result<T, E> で戻り値として返す。
  • ? は「成功なら取り出す、失敗なら return」の省略記法。
  • ? を使う関数自身が Result を返す必要がある。main も Result を返せる。
  • エラー型は列挙型 ＋ Display ＋ Error。手で書くなら thiserror、アプリなら anyhow。
  • panic! は「起こってはならないこと」だけ。ライブラリでは避ける。
  • 署名を見れば失敗しうるか分かる。これが例外との最大の違い。
