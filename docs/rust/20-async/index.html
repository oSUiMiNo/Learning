第20章 async / await — C# の Task と何が違うか

見た目はそっくりですが、動き方が根本的に違います。Rust の Future は、誰かが await するまで 1 行も走りません。ここは必ず読んでください。

この章は必ず読んでください。 C# の async の知識が、そのままでは通じません。

見た目はそっくりです。async fn と書き、.await と書きます。 けれど動き方が根本的に違います。1 行で言えばこうです。

いちばん大事な違い
動き始めるタイミング
C#async メソッドを呼んだ時点で、もう走っている
Rust.await されるまで、1 行も走らない

C# の Task は「ホット」、Rust の Future は「レイジー」と呼ばれます。

実際に確かめる

200 ミリ秒かかる関数を呼んで、すぐに時間を測ってみます。

この違いが引き起こすこと
場面C#Rust
await を書き忘れた 処理は走るが結果を待たない。例外が消えることも（投げっぱなし） 処理が走らない。unused_must_use 警告が出る
2 つを同時に走らせたい 呼んでおいて、後で両方 await それでは直列になる。join! が必要
結果を捨てたい _ = FooAsync(); で走る 走らない。spawn が必要

2 行目が実務でいちばん危険です。 C# の癖で書くと、並行になっているつもりで直列になります。

直列と並行

Task.WhenAll との対応
C#Rust (tokio)
await Task.WhenAll(a, b)tokio::join!(a, b)
await Task.WhenAny(a, b)tokio::select! { .. }
Task.Run(...)tokio::spawn(...)
await Task.Delay(100)tokio::time::sleep(..).await
cts.CancelAfter(50)tokio::time::timeout(.., fut).await
結果が全部 Result ならtry_join! で最初の失敗で打ち切れる

join! と WhenAll の違いに注意してください。 WhenAll は「すでに走っているものを待つ」、 join! は「これから同時に走らせる」です。

ランタイムを自分で選ぶ

Rust の標準ライブラリには、非同期処理を動かす仕組みが入っていません。 async は構文だけで、実行する人がいないのです。

.NET ランタイムが無いということ

C# では async を書けば、.NET のスレッドプールが勝手に面倒を見てくれます。 考える必要がありません。

Rust ではランタイムを選んで入れます。 面倒ですが、代わりに「組み込み機器向けの軽いもの」 「1 スレッドで動かすもの」など、用途に合わせて選べます。

ランタイム特徴
tokio事実上の標準。ネットワーク周りが充実。迷ったらこれ
async-std標準ライブラリに似た API
smol小さい。組み込み向け
embassy組み込み専用
ランタイムを混ぜられない

tokio を前提に書かれたクレートは、 async-std の上では動かないことがあります。 「どのランタイム向けか」がクレート選びの条件になります。

実質 tokio が標準なので、 特別な理由がなければ tokio を選んでおけば困りません。

spawn だけは C# と同じ

tokio::spawn に渡したものは、ランタイムが引き取るので即座に走り始めます。

使い分け
やりたいこと書き方
1 つ待つfut.await
複数を同時に待つjoin!(a, b)
先に終わったほうを採るselect! { .. }
投げて後で回収するtokio::spawn(fut)
数が動的に決まるspawn して Vec<JoinHandle> に集める

async のつらいところ

async は「別の色の関数」になる

async fn は、ふつうの関数から直接呼べません。 .await は async の中だけで使えるからです。

そのため一度 async にすると、呼び出し側も全部 async にする必要があります。 これは C# でも同じ現象（"async all the way"）ですが、 Rust ではトレイトのメソッドにも波及するので、より厄介です。

対処としては、そもそも async が必要か考えるのがいちばんです。 「同時に何千も待つ」のでなければ、スレッド（第 19 章）で十分なことが多いです。

await をまたいでロックを持たない

Mutex をロックしたまま .await すると、 他のタスクが同じロックを待ってデッドロックすることがあります。

どうしてもまたぎたい場合は tokio::sync::Mutex を使います （こちらは .await でロックを取ります）。 ただし遅いので、まず設計で避けるのが正解です。

Future の正体

Future は「poll() されると、 Ready(値) か Pending を返すもの」というだけのトレイトです。

ランタイムがこれを繰り返し呼び、Pending が返る間は他のタスクに切り替えます。 誰も poll() しなければ何も起きない ── これが「await されるまで走らない」の正体です。

C# のステートマシン変換と発想は同じですが、 C# は変換した時点でスレッドプールに投入され、Rust は投入されません。

全体を動かす

やってみよう
  1. examples/20-async を動かして、経過時間を確認してください。2 番目（直列）と 3 番目（並行）の差が要点です。
  2. tokio::join! の 2 つを、それぞれ別々に .await する形に書き換えて、時間が倍になることを確認してください。
  3. let future = fetch(...) の .await を消して、警告が出ることを確認してください。C# なら黙って走ってしまう場面です。
  4. #[tokio::main] を消して、どんなエラーになるか見てください。
  5. timeout の 50ms を 600ms に変えて、間に合うようになることを確認してください。

この章のまとめ

  • Rust の Future は .await されるまで走らない。C# の Task は呼んだ時点で走る。
  • だから「呼んでおいて後で await」では並行にならない。join! を使う。
  • await 忘れは C# では投げっぱなし、Rust では未着手。警告で気づける。
  • ランタイムは標準に無い。実質 tokio を入れる。
  • tokio::spawn に渡したものだけは即座に走る。
  • .await をまたいで Mutex を持たない。
  • 同時に何千も待つのでなければ、スレッド（第 19 章）で足りることが多い。
