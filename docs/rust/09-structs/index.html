第9章 構造体と impl — クラスがない代わりに

Rust に class はありません。データは struct、ふるまいは impl に分けて書きます。そして継承がありません。その埋め合わせ方まで見ます。

Rust に class はありません。 データは struct、ふるまいは impl に分けて書きます。 そして継承がありません。

慌てなくて大丈夫です。C# でも「継承より合成」と言われますし、 Rust はその方針を言語レベルで徹底しただけです。 埋め合わせの方法もちゃんとあります。

データとふるまいを分けて書く

impl ブロックは何個でも書ける

impl は同じ型に対して複数書けます。 ファイルを分けることもできます。 C# の partial class に近い自由度がありますが、 あちらと違って宣言に partial は要りません。

「データの定義」と「機能ごとのふるまい」を分けて置けるので、 大きな型でも見通しが保てます。

self の 3 つの形 — ここが C# に無い

メソッドの第 1 引数には self を書きます。 そして3 つの形があり、意味がまったく違います。

書き方意味C# なら呼んだ後
&self借りて読むふつうのメソッドそのまま使える
&mut self借りて書き換えるふつうのメソッド（変更あり）そのまま使える（呼び出し側に mut が必要）
self所有権をもらって消費する対応するものが無いもう使えない
（なし）関連関数static メソッド—
self を取るメソッドを呼ぶと、変数が使えなくなる

into_summary(self) は所有権をもらいます。 つまり呼んだ後、その変数は使えません。

面倒に見えますが、これは「この値はもう使うな」と設計者が表明できる仕組みです。 ファイルを閉じる、接続を切る、変換して別の型にする、といった 「一度きりの操作」を型で守れます。

名前の慣習も決まっています。into_ で始まるメソッドは 所有権をもらうという合図です。

名前の慣習
接頭辞self の形意味
as_&self安く別の見え方にする（as_str）
to_&self複製して作る（to_string）
into_self消費して変換する（into_iter）
newなし作る。C# のコンストラクタ相当

この慣習は標準ライブラリ全体で守られているので、 メソッド名を見ただけで所有権の扱いが読めます。

derive で「よくある能力」を手に入れる

C# なら ToString() や Equals() は object から継承されて最初からあります。 Rust には object がないので、必要な能力を明示します。

何も付けないと、デバッグ表示すらできません。

言われたとおり 1 行足せば直ります。

derive できる主なもの
deriveできることC# なら
Debug{:?} で表示ToString()（デバッグ用）
Clone.clone()ICloneable
Copy代入でコピー値型（struct）
PartialEq== で比較Equals / IEquatable
PartialOrd< > で比較IComparable
HashHashMap のキーにできるGetHashCode
DefaultDefault::default()既定値のコンストラクタ

record 型を書いたときに C# が自動生成するものと、ほぼ同じ一覧です。 Rust では 1 つずつ選べる、という違いだけです。

人間に見せる表示（ToString() に当たるもの）は Display トレイトを自分で実装します。これは derive できません。 「どう見せるか」は自動では決められないからです（第 11 章で書きます）。

一部だけ変えて作る

..book が「残りは book と同じ」という意味です。 C# の with 式とほぼ同じ働きです。

.. は move する

..book は残りのフィールドをmove します。 String のような Copy でないフィールドが残っていると、 book はその後使えなくなります。 使い続けたいなら ..book.clone() にしてください。

タプル構造体で単位を分ける

名前を付けるだけの構造体も作れます。これが意外に強力です。

これが「newtype パターン」

C# でも record struct Yen(uint Value); のように書けますが、 Rust ではこの書き方が日常的に使われます。

UserId(u32) と OrderId(u32) を分ければ、 引数の順番を間違えたときにコンパイルエラーになります。 実行時のコストはゼロです（コンパイル後は生の u32 と同じ）。

第 14 章に出てくる孤児則を回避するときにも、この書き方を使います。

継承が無いことへの対処

継承の 3 つの用途を、それぞれ別の道具で置き換える
継承で何をしたかったかRust での書き方
共通のふるまいを共有するトレイトの既定実装（第 14 章）
共通のデータを共有するフィールドとして持たせる（合成）
いろいろな型を同じものとして扱うdyn Trait か enum（第 10・14 章）

「基底クラスのフィールドを使いたい」という場面は、 その基底クラスをフィールドとして持つ形に書き換えます。

最初は冗長に感じますが、 「どのフィールドがどこから来たか」が常に見えるという利点があります。

全体を動かす

やってみよう
  1. examples/09-structs を動かしてください。
  2. #[derive(Debug, ...)] の Debug を消して、E0277 を出してください。
  3. book.into_summary() の後に println!("{book:?}"); を足して、E0382 を確認してください。
  4. finish() を呼ぶ行の前で、let mut book の mut を消してみてください。&mut self のメソッドが呼べなくなることが分かります。
  5. Yen と Dollar を足そうとして、コンパイルエラーになることを確認してください。

この章のまとめ

  • データは struct、ふるまいは impl。impl は何個でも書ける。
  • &self（読む）/ &mut self（書く）/ self（消費する）の 3 つ。3 番目は C# に無い。
  • into_ で始まるメソッドは所有権をもらう合図。
  • 能力は derive で足す。C# の record が自動生成するものとほぼ同じ一覧。
  • 継承は無い。ふるまいはトレイト、データは合成、多態は dyn か enum で置き換える。
  • タプル構造体（newtype）で単位を型として分けると、取り違えがコンパイルエラーになる。
