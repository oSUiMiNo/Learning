第17章 テストとドキュメント — 標準で付いてくるもの

テスト機構は言語に組み込みです。さらに「ドキュメントに書いた例がテストとして走る」仕組みまであります。この教材自身もそれに支えられています。

テストは言語に組み込まれています。 NUnit や xUnit のような外部のフレームワークを入れる必要はありません。

そして Rust には C# に無い仕組みが 1 つあります。 ドキュメントに書いたコード例が、テストとして実行されます。 「ドキュメントの例が古くなって動かない」が構造的に起きません。 この教材自身も、同じ考え方で作られています。

書き方

対応表
C# (xUnit)Rust
[Fact]#[test]
[Theory] + [InlineData]ループを書く、または rstest クレート
Assert.Equal(a, b)assert_eq!(a, b)
Assert.NotEqualassert_ne!
Assert.Trueassert!
Assert.Throws<T>#[should_panic]
[Skip]#[ignore]
dotnet testcargo test
テストは別プロジェクト同じファイルに書くのが慣習

最後の行が大きな違いです。 Rust ではテストを実装と同じファイルに置きます。 #[cfg(test)] が付いているので、通常のビルドには含まれません。 製品のバイナリにテストコードが混ざる心配はありません。

同じファイルにあるので、非公開の関数もテストできます。 C# で InternalsVisibleTo を書く必要があった場面が、そのまま解決します。

テスト関数の名前は日本語でよい

Rust の識別子は Unicode を許すので、テスト名に日本語が使えます。 出力にもそのまま出るので、読みやすさのために使う価値があります。

ふつうの関数名に日本語を使うと警告が出ますが（non_snake_case）、 テストでは実害がないので使われることがあります。

ドキュメントテスト

これが Rust 独自の仕組みです。 /// のドキュメントコメントの中に ``` でコードを書くと、 それが実際にコンパイルされ、実行されます。

実行するとこうなります。

3 種類のテストが一度に走る
種類置く場所見えるもの
単体テスト実装と同じファイルの #[cfg(test)] mod tests非公開のものも見える
結合テストtests/*.rs公開している API だけ
ドキュメントテスト/// の中の ```公開している API だけ

結合テストは別のクレートとしてコンパイルされます。 だから「公開している API だけで目的を果たせるか」の検証になります。 C# で別プロジェクトからテストするのと同じ位置づけです。

なぜドキュメントテストが効くのか

C# の XML ドキュメントコメントに書いた <example> は、 ただのテキストです。API を変えても誰も気づきません。

Rust では、それがコンパイルエラーになります。 「使い方の例」と「実際の API」が食い違えないのです。

docs.rs で公開されているクレートのドキュメントに載っているコードは、 すべてこの検証を通っています。 だから公式ドキュメントのサンプルは、写せば動きます。 これは Rust のエコシステム全体の信頼性を支えている仕組みです。

テストの中で ? を使いたいなら、Result を返すようにします。 前準備が短くなります。

走らせ方

コマンドやること
cargo test全部走らせる
cargo test 税込み名前に含むものだけ
cargo test -- --nocaptureprintln! の出力を見せる
cargo test -- --ignored#[ignore] のものだけ
cargo test -- --test-threads=11 つずつ順番に走らせる

println! が出ないのは既定の動作

テストが通っている間、println! の出力は隠されます。 デバッグのために見たいときは -- --nocapture を付けてください。

-- の前が cargo への引数、後がテストランナーへの引数です。 この区切りを忘れると cargo が知らない引数だと怒ります。

テストは並列に走る

既定では複数のスレッドで同時に走ります。C# の xUnit と同じです。 同じファイルを読み書きするテストは、そのままだと衝突します。

対処は 3 つあります。

  • テストごとに違う一時ディレクトリを使う（tempfile クレート）
  • --test-threads=1 で直列にする
  • そもそもファイルに触らない設計にする（依存を引数で渡す）

ドキュメントを生成する

自分のコードと、依存しているすべてのクレートのドキュメントが生成され、 ブラウザで開きます。

ドキュメントコメントの書き方
記法説明する対象
///次に来る項目（関数・構造体など）
//!そのファイル自身（モジュール・クレート）

中身は Markdown です。慣習的な見出しがあります。

やってみよう
  1. examples/17-testing で cargo test を走らせてください。
  2. with_tax のドキュメントの assert_eq!(with_tax(100, 0.10), 110); を 111 に変えて、ドキュメントテストが落ちることを確認してください。これがこの章の要点です。
  3. cargo test -- --ignored で、#[ignore] のテストが走ることを確認してください。
  4. cargo test 日本語 のように名前で絞り込んでください。
  5. cargo doc --open でドキュメントを生成し、書いた # 例 がどう表示されるか見てください。

この章のまとめ

  • テスト機構は言語に組み込み。#[test] と cargo test だけ。
  • テストは実装と同じファイルに #[cfg(test)] mod tests で書く。非公開のものもテストできる。
  • tests/ の結合テストは別クレート。公開 API だけを使う検証になる。
  • ドキュメントの ``` の中のコードがテストとして走る。これが Rust 独自の強み。
  • println! を見たいときは cargo test -- --nocapture。
  • テストは並列に走る。ファイルを触るテストは注意。
