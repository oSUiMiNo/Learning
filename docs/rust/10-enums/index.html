第10章 列挙型と match — null が消える仕組み

Rust の enum は値を持てます。だから `Option<T>` で「無いかもしれない」を型として表せて、null 参照例外という概念そのものが無くなります。

C# の enum は、整数に名前を付けたものです。 Rust の enum はそれぞれの選択肢が値を持てます。 これは別物と考えたほうがよく、F# の判別共用体や TypeScript の直和型に近いものです。

そしてこの仕組みのおかげで、Rust には null がありません。 null 参照例外という概念そのものが消えます。この章の主題はそこです。

値を持てる列挙型

C# でこれをやるには

C# で同じことを表現するなら、抽象クラスか interface を作って Circle、Rectangle、Triangle の 3 クラスを継承させます。

Rust の enum はそれを 1 つの型で表したものです。 利点は 2 つあります。

  • ヒープ確保が起きない（クラスならインスタンスごとに確保が必要）
  • 選択肢が閉じているので、match で漏れを検出できる

C# 側でも近年は abstract record ＋ パターンマッチで似た書き方をしますが、 「他の誰かが勝手に派生クラスを増やせる」ので網羅性は保証されません。

match で分解する

match は分岐と同時に中身を取り出します。 C# の is パターンや switch 式の分解と同じ働きです。

網羅性がエラーになる

これが列挙型のいちばんの価値

列挙型に選択肢を足したとき、直すべき場所を全部コンパイラが教えてくれます。

「支払方法に新しい種類を追加したら、対応し忘れた画面があった」 という種類の不具合が、原理的に起きません。 C# で同じ安全性を得るには、テストを書くか、レビューで気づくしかありません。

逆に _ => ...（それ以外）を書くと、この恩恵を捨てることになります。 本当に「それ以外は同じ扱い」のときだけ使ってください。

Option — null の代わり

標準ライブラリの Option<T> は、ただの列挙型です。

これだけです。特別な言語機能ではありません。 そしてこれが C# の null の役目を全部引き受けます。

nullable 参照型との違い

C# 8 の nullable 参照型（User?）は、かなり近いところまで来ています。 しかし決定的な違いが 2 つあります。

C# の User?Rust の Option<User>
破ったとき警告（設定次第で無効化できる）コンパイルエラー
実行時の表現同じ参照。null が入りうる別の型。None は値のひとつ
入れ子User?? は書けないOption<Option<T>> が書ける
既存コードとの互換後付けなので抜け穴がある最初からこれしかない

「後付けの警告」と「最初からある型」の差です。 Rust では Option を通らずに中身に触る方法が存在しません。

Option の開け方

書き方意味C# なら
match opt { Some(v) => .., None => .. }両方を扱うif (x != null) ... else ...
if let Some(v) = opt { }あるときだけif (x != null) { }
let Some(v) = opt else { return; };無ければ抜ける早期 return のガード節
opt.unwrap_or(既定値)無ければ既定値x ?? 既定値
opt.unwrap_or_default()無ければ型の既定値x ?? default
opt.map(|v| ..)あれば変換x?.Foo()
opt.and_then(|v| ..)あれば次も Option を返す処理へx?.Foo()?.Bar()
opt.unwrap()無ければ panicx!（null 免除演算子）
opt.expect("説明")無ければ panic（説明付き）—
opt.is_some() / is_none()あるか無いかだけ調べるx != null
?. の対応が map と and_then

C# の ?. を連ねる書き方は、Rust では map / and_then になります。

見分け方: 渡す関数が Option を返すなら and_then、 ふつうの値を返すなら map です。 map に Option を返す関数を渡すと Option<Option<T>> になってしまいます。

unwrap() を書き散らさないこと

unwrap() は「無ければ panic」です。C# の x! と同じで、 「絶対にあると分かっている」という主張です。

学習中や書き捨てでは便利ですが、残しておくと本番で落ちます。 最低限 expect("なぜあるはずなのかの説明") にしておくと、 落ちたときに原因が分かって助かります。

let else — 早期 return を素直に書く

「無ければ抜ける」を書くための構文です。C# のガード節に相当します。

let else は比較的新しい構文

let ... else が使えるようになったのは Rust 1.65（2022 年）です。 それより前の記事では、同じことを次のように書いています。

どちらも今も動きますが、let else のほうが短く読めます。

if let と while let

let 連鎖（let chains）

if let を && でつなげて書けます。

これは長く待たれていた機能で、安定版で使えるようになったのはごく最近です （2024 エディション以降）。それより古い記事では 「入れ子の if let を書くしかない」と説明されています。

全体を動かす

やってみよう

  2. Shape に Square { side: f64 } を足して cargo build してください。area() の match がエラーになることを確認してください。これがこの章の要点です。

この章のまとめ

  • Rust の enum は選択肢ごとに値を持てる。C# の enum とは別物。
  • match は網羅していないとコンパイルエラー。選択肢を足すと直す場所が全部分かる。
  • Option<T> はただの列挙型。これが null の役目を引き受ける。
  • C# の nullable 参照型は警告、Rust の Option はエラー。抜け穴が無い。
  • ?. は map / and_then、?? は unwrap_or、! は unwrap。
  • unwrap() は最終的に expect("理由") か、ちゃんとした分岐に置き換える。
