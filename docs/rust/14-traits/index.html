第14章 トレイトとジェネリクス — インターフェースとの違い

トレイトはインターフェースによく似ていますが、「後から他人の型に実装できる」点が決定的に違います。単相化の話も避けずにやります。

トレイトはインターフェースによく似ています。 「このメソッドを持っていること」を約束する仕組み、という点は同じです。

違いは 1 つですが、それが決定的です。 トレイトは、他人が作った型にも後から実装できます。 C# の拡張メソッドでは真似できない範囲まで、これができます。

まず似ているところ

既定実装まで含めて、ほぼ同じです。 書き方の違いは impl Trait for Type という形だけです。

実装を型の宣言と切り離す

C# は class Person : IGreet と、クラス宣言に書きます。 Rust は impl Greet for Person と、別の場所に書きます。

つまり型を定義したファイルと、トレイトを実装するファイルを分けられます。 これが次の節の話につながります。

決定的な違い — 他人の型に実装できる

拡張メソッドとの違い

C# の拡張メソッドも int にメソッドを足せます。しかし決定的に違います。

C# の拡張メソッドRust のトレイト実装
メソッドを足せるできるできる
インターフェースを実装させるできないできる
ジェネリクスの制約に使える使えない使える
多態に使える使えない使える（dyn Trait）

C# では「int に IGreet を後から実装させる」ことは不可能です。 だから List<IGreet> に int を入れることもできません。

Rust ならできます。この違いのおかげで、 ライブラリの型を自分のシステムに組み込むのがはるかに楽です。 たとえば serde は「あらゆる型を JSON にできる」仕組みを、 この性質だけで実現しています。

孤児則 — できないこともある

無制限ではありません。1 つ制約があります。

孤児則を回避する — newtype

「標準の Vec に標準の Display を実装したい」ときは、 自分の型で包みます（第 9 章のタプル構造体）。

包んだぶんの実行時コストはゼロです。 コンパイル後は生の Vec と同じになります。

ジェネリクスとトレイト境界

書き方は 3 通りあり、どれも同じ意味です。

使い分け
  • 境界が 1 つで短いなら impl Trait
  • 同じ型を複数の引数で使うなら <T: Trait>
  • 境界が長い・複数あるなら where

単相化 — C# のジェネリクスとの違い

.NET のジェネリクスとの比較

.NET は参照型については 1 つの実体を共有し、 値型については型ごとにコードを作ります。

Rust は常に型ごとに作ります（単相化）。だから

  • 呼び出しは直接。インライン展開もされる。実行時コストがゼロ
  • そのぶん実行ファイルが大きくなり、ビルドが遅くなる
  • 実行時に型情報が残らない。C# の typeof(T) のようなことは基本できない

3 つ目が実務で効きます。C# のリフレクションに相当するものは Rust にはほぼ無く、 「型に応じて動きを変える」ことはコンパイル時に決めます。

dyn Trait — 違う型を混ぜる

ジェネリクスでは「1 つの Vec に Person と Robot を混ぜる」ことができません。 そのときは dyn を使います。

List<IGreet> に相当するもの

C# の List<IGreet> がそのまま Vec<Box<dyn Greet>> です。 Box が必要なのは、要素の大きさが型によって違うからです。

C# では参照型なのでポインタ 1 個ぶんに揃っていますが、 Rust の値は型ごとに大きさが違うので、 ヒープに置いてポインタで揃える必要があります。それが Box の役目です。

借用でよければ &dyn Greet と書けて、Box は要りません。

dyn にできないトレイトがある

dyn Trait にするには、そのトレイトが オブジェクト安全である必要があります。主な条件は次の 2 つです。

  • メソッドがジェネリック型引数を持たない
  • self を値で受け取るメソッドが無い（Sized が要るため）

the trait cannot be made into an object と言われたら、これです。 ジェネリックなメソッドがあるトレイトは dyn にできません。

第 11 章の ? がエラー型を自動変換していたのは、この仕組みです。

全体を動かす

やってみよう
  1. examples/14-traits を動かしてください。
  2. impl Greet for String を足して、"あ".to_string().hello() を呼んでみてください。
  3. impl std::fmt::Display for Vec<i32> を書こうとして、孤児則のエラー（E0117）を見てください。
  4. trait Greet に fn convert<T>(&self) -> T; のようなジェネリックなメソッドを足して、dyn Greet が使えなくなることを確認してください。
  5. greet_all を &[Box<dyn Greet>] を受け取る形に書き換えてみてください。

この章のまとめ

  • トレイトはインターフェースに似ているが、他人の型にも後から実装できる。
  • ただし孤児則がある。「型かトレイトの一方は自分のもの」であること。回避策は newtype。
  • ジェネリクスは単相化される。実行時コストゼロだが、実行時の型情報は残らない。
  • 違う型を 1 つの箱に混ぜたいときだけ dyn Trait。C# の List<IFoo> に相当。
  • 境界の書き方は <T: Trait> / impl Trait / where の 3 通り。意味は同じ。
  • Display は derive できない。人間向けの表示は自分で決めるもの。
