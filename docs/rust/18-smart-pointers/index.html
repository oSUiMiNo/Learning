第18章 スマートポインタ — Box, Rc, RefCell

「所有者はひとりだけ」では書けない形が出てきたときの道具です。参照カウントと、実行時に借用を検査する仕組みを使い分けます。

「持ち主はひとりだけ」という規則は強力ですが、それでは書けない形もあります。

  • 再帰的なデータ構造（木、連結リスト）
  • 複数の場所から同じものを見たい（親子の相互参照、キャッシュ）
  • 外から見ると不変なのに、中身を書き換えたい

そのための道具が用意されています。4 つ覚えれば足ります。

使い分け

型役目C# なら
Box<T>中身をヒープに置く。持ち主は 1 人ふつうの参照型（ただし共有はしない）
Rc<T>参照カウントで共有。単一スレッドふつうの参照型
Arc<T>同じ。スレッドをまたげるふつうの参照型
RefCell<T>借用の検査を実行時に回す—（C# は常にこれ相当）
Weak<T>カウントを増やさない参照WeakReference

Box — 再帰的なデータ構造

次の enum は、Box が無いと定義できません。

なぜ Box が必要なのか

Rust はコンパイル時に「この型は何バイトか」を決めます。 Node(Tree, Tree) と書くと、 Tree の大きさを決めるために Tree の大きさが必要になり、 無限に続いてしまいます。

Box<Tree> はポインタなので、常に 8 バイトです。 大きさが決まるので定義できるようになります。

C# ではクラスが常に参照なので、この問題が起きません。 かわりにすべてのオブジェクトが必ずヒープに置かれます。 Rust は「ヒープに置くかどうか」を選べる、という違いです。

Rc — 複数の持ち主

これが C# の「ふつう」

C# でクラスのインスタンスを 3 つの変数に代入すれば、 3 か所から同じものが見えます。それが既定の動作です。

Rust ではそれを明示的に選ぶことになります。 Rc と書くことで「これは共有されている」ことがコードに現れます。

Rc::clone(&doc) と書く慣習にも意味があります。 doc.clone() でも同じですが、 前者だと「中身の複製ではなくカウントの増加だ」と読み手に伝わります。

Rc は書き換えられない

Rc<T> から得られるのは &T だけです。 複数の持ち主がいるので、書き換えを許すと借用規則が破れます。

共有したうえで書き換えたいときは、内側に RefCell を包みます。 それが次の話です。

RefCell — 内部可変性

RefCell は「借用の検査をコンパイル時ではなく実行時に行う」箱です。

なぜこれが要るのか

「外から見ると不変なのに、中では状態を持ちたい」場面があります。 キャッシュ、呼び出し回数の記録、遅延初期化などです。

C# なら private int _hits; を書けば済みます。 Rust では &self のメソッドから書き換えられないので、 RefCell で「実行時に検査する」ことを選びます。

RefCell は破ると panic する

検査が実行時なので、規則を破るとコンパイルは通り、実行時に落ちます。

メッセージは already borrowed: BorrowMutError です。 落ちてほしくないなら try_borrow_mut() を使って Result で受けてください。

コンパイル時の安全を、実行時の安全と引き換えにしていることを 忘れないでください。使うのは本当に必要な場面だけです。

Rc + RefCell — 定番の組み合わせ

「共有したうえで書き換えたい」ときの形です。 C# のふつうのオブジェクト共有に、いちばん近い状態になります。

C# の楽さと引き換えているもの

Rc<RefCell<T>> は、C# なら何も書かずに得られる状態です。 Rust ではそれが冗長に見えます。

ただし C# 側にも代償があります。 「このオブジェクトはどこから書き換えられるのか」が分からないという代償です。 Rust では Rc<RefCell<T>> と型に書いてあるので、 共有可変であることが一目で分かります。

そして重要なのは、ほとんどの場面ではこれが要らないことです。 まず所有権と借用で書けないか考えてください。 Rc<RefCell<T>> が増えてきたら、設計を見直す合図です。

Weak — 循環参照を避ける

Rc だけでは漏れる

親が子を Rc で持ち、子が親を Rc で持つと、 カウントが 0 にならず永遠に解放されません。

C# の GC は循環参照を検出できるので問題ありませんが、 参照カウント方式では検出できません。 ここは C# より弱い部分です。

片方を Weak にすれば解決します。

Deref — Box が透過的に見える理由

なぜ box.method() と書けるのか

Box<String> に対して .len() と書けます。 Box に len() は無いのに動きます。

これは Deref トレイトのおかげです。 メソッドが見つからないとき、Rust は 自動的に参照を外して探しに行きます（自動参照外し）。

この型にこれが自動で使える
Box<T>T のメソッド
Rc<T>T のメソッド
String&str のメソッド
Vec<T>&[T] のメソッド

String に &str のメソッドが使えるのも、これが理由です。 第 8 章で「引数は &str で受ければ String も渡せる」 と書いたのは、この仕組みによるものです。

全体を動かす

やってみよう
  1. examples/18-smart-pointers を動かして、Rc のカウントの変化を確認してください。
  2. enum Tree の Box を外して、E0072（無限のサイズ）を出してください。
  3. let first = cell.borrow(); の後の try_borrow_mut() を borrow_mut() に変えて、実行時に panic することを確認してください。
  4. Child の Weak<Parent> を Rc<Parent> に変えて、strong_count がどうなるか観察してください。

この章のまとめ

  • Box<T> はヒープに置くだけ。再帰的なデータ構造に必要。
  • Rc<T> は参照カウントで共有。C# の参照型の既定の動作にあたる。
  • Rc は読み専用。書きたいなら Rc<RefCell<T>>。
  • RefCell は検査が実行時。破ると panic する。
  • 循環参照は参照カウントでは解放されない。片方を Weak にする。
  • Rc<RefCell<T>> が増えてきたら、設計を見直す合図。
  • Deref のおかげで Box や String は中身のメソッドが透過的に使える。
